# ДЗ 1 — Архитектура системы Маркетплейса

## Выбор архитектурного стиля

### Контекст и проблематика

Необходимо спроектировать бэкенд для маркетплейса (каталог, заказы, оплата, персонализированные ленты, уведомления). Основная задача — обеспечить **масштабируемость** отдельных доменов и позволить командам работать независимо, не допуская деградации системы в «распределенный монолит».

### Решение: Микросервисная архитектура

Система разбита на независимые сервисы. Каждый сервис имеет свою бизнес-логику и взаимодействует с остальными только через стабильные REST-апи.

#### Декомпозиция и границы

- **API Gateway**: Единая точка входа для Покупателя и Продавца.
- **User Service**: Регистрация, аутентификация, профили покупателей и продавцов.
- **Catalog Service**: Управление товарами.
- **Feed Service**: Персонализированная лента — скоринг по истории покупок и просмотров.
- **Order Service**: Жизненный цикл заказа: создание, резервирование, статусы.
- **Payment Service**: Инициирование платежа, интеграция с платежным шлюзом, транзакции.
- **Notification Service**: Уведомления о статусах заказов (email, push).

Принцип **Information Hiding** соблюден: `Order Service` не знает о реализации `Payment Service` и взаимодействует с ним только через REST.

#### Управление связанностью

Для минимизации **Coupling** между сервисами применены следующие стратегии:

1. **Database per Service**: У каждого сервиса своя PostgreSQL-база, что исключает **Common Coupling** и сохраняет владение данными внутри домена.
2. **API Gateway как фасад**: Скрывает внутреннее устройство системы от внешних клиентов — Покупатель и Продавец обращаются только к Gateway по `HTTP/REST`.
3. **Синхронный REST**: Взаимодействие между сервисами (`Order → Payment`, `Order → Notification`, `Payment → Notification`).

## Trade-offs

| Критерий | Почему это важно для Маркетплейса |
|---|---|
| **Масштабируемость** | В пиковые нагрузки масштабируем только `Catalog` и `Feed`, не затрагивая всю систему. |
| **Operational Complexity** | Принимаем сложность ради возможности **независимого развертывания** команд. |
| **Data Integrity** | Каждый сервис владеет своими данными, межсервисная согласованность достигается через явные REST-коллы |
| **Network Latency** | Межсервисные вызовы добавляют задержки по сравнению с монолитом. |

#### Альтернатива 1: Модульный Монолит

- Единый развертываемый модуль со строго разделенными пакетами для каждого домена.
- **Плюсы:** простое развертывание, нулевая сетевая задержка, единая транзакция БД.
- **Минусы:** масштабирование либо всех доменов, либо никаких, риск роста связанности со временем.

#### Альтернатива 2: Сервис-ориентированная архитектура

- Более крупные сервисы с общей шиной данных (например,ESB).
- **Плюсы:** повторное использование корпоративных возможностей.
- **Минусы:** ESB становится узким местом и единой точкой отказа.

## Техническая реализация

Сервис реализован на **FastAPI** , запускается через `uvicorn` на порту `8000`. Образ собирается на базе `python3.11`.

### Структура сервиса

```
service/
├── main.py            
├── requirements.txt   
└── Dockerfile        
docker-compose.yml
architecture.c4
```

### Запуск через Docker Compose

```bash
docker-compose up --build -d
```

### Запуск вручную

1. **Сборка образа:**

```bash
docker build -t marketplace-service ./service
```

2. **Запуск контейнера:**

```bash
docker run -d -p 8000:8000 --name marketplace-app marketplace-service
```

3. **Health check:**

```bash
curl http://localhost:8000/health
# {"status": "OK", "service": "api-gateway"}
```

4. **Остановка:**

```bash
docker-compose down
```

## Визуализация архитектуры - C4 Model

Архитектура зафиксирована на уровне **Container (C4 Level 2)** в файле [`architecture.c4`](./architecture.c4). Основные компоненты:

- **API Gateway**: Единая точка входа, скрывающая внутреннее устройство системы.
- **6 микросервисов**: `User`, `Catalog`, `Feed`, `Order`, `Payment`, `Notification`.
- **Isolated DBs**: У каждого сервиса своя PostgreSQL-база (Database per Service).
- **REST**: Все межсервисные взаимодействия синхронные, через REST.

## Итог

**Выбранный вариант:** Микросервисная архитектура с REST-взаимодействием через API Gateway и изолированными PostgreSQL-базами для каждого сервиса — обеспечивает независимое масштабирование и независимый деплой при допустимом росте операционной сложности.
